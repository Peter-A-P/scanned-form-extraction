Every field graded by code against a known answer

A small vision model you own beats Azure's document AI on half the forms tested and matches it on the rest, for a fraction of the price

Every organisation that still takes paper has someone typing forms in. There are three ways to hand that to a machine: pay a frontier AI model by the page, buy a managed document service, or fine-tune a small open model and run it yourself. They are rarely measured on the same pages. This project measured them, with page reads. Twelve readers, from Claude, GPT and Gemini to Azure Document Intelligence, classic OCR pipelines, and a 2B and a 4B Gemma model fine-tuned here, read the same public pages, many of them several times: clean and degraded, development and test, three training seeds, and second reads. Every field they wrote was graded by code against the answer the dataset records.

      Why it is a fair fight with Azure

      • Same pages, same grader. Both read the same test documents, at the same resolution, and one programmatic grader scored every field of both.
      • Both were trained on the forms. Azure's custom neural models were trained on 100 labelled documents of each registration and ad-buy training split and 30 of each tax-form face; the fine-tunes on . On registration and ad-buy forms neither saw a page of the form design it was tested on.
      • Azure was not handicapped on receipts. CORD's receipts went to Azure's own prebuilt receipt model, untrained, at its lower price.

      How it was fine-tuned

      Two open-weights bases from Google, Gemma 4 E2B and E4B, each fine-tuned per kind of form with QLoRA: the base model's weights are frozen and stored in 4 bits, and only small low-rank "adapter" matrices beside its attention and feed-forward layers are trained, on the page images directly. That is what lets a vision model train on one 24 GB card in minutes rather than on a cluster.

      What the recipe's choices were worth

      Three changes to the recipe, each trained once and read like the headline models. Halving the visual tokens and cutting the training documents cost accuracy on every form type measured; one model for every form type gained on registration forms and lost on ad-buy and tax forms. The headline recipe stands: 1,120 visual tokens a page, the whole training set, one model per form type.

      From scanned page to served model

      1. 1Pair each page with its answer. The page image, and the fields the dataset records for it as the exact JSON the grader marks. Form designs held out for testing never reach training, and a held-out document refuses the training set.
      2. 2Train on the answer only. One turn of page images and the same instruction every other reader is sent, one turn of the JSON. The loss falls on the answer's tokens, so it learns to read, not to recite the prompt.
      3. 3Keep the vision tower whole. The image encoder, its projector and the output layer stay at full precision; the adapter trains the projector and the language layers. A first run that quantised the tower failed at its first step.
      4. 4Checkpoint from the first steps. Rented cards can be taken back, so every checkpoint goes to object storage and a run resumes from its newest.
      5. 5Serve it plainly. vLLM on one RTX 3090 at temperature 0. Forcing the output into the schema's grammar was tried and rejected: it pushed the models off the format they were trained on.
      6. 6Grade it once, publish it. Each test set read once, graded by the same code as every other reader, and the adapters published with cards that list their failure modes.

      Serving it: what one card does

      Each fine-tune was served on its own on one rented at an hour, behind the same gateway as the frontier APIs, and read by a closed-loop client with 1, 8 and 32 requests in flight for three minutes each. Pages a second climb with the load until the card is full; the time to read one document climbs too.

      In practice. A 2B fine-tune and vLLM fit on one consumer 24 GB card with room for 32 requests at once. No page leaves the building: for records that cannot go to a vendor, that matters more than the price. The card is paid by the hour whether it is busy or not, so what a page really costs depends on how full you keep it, which is what the calculator below is for.

      Your break-even

      An API is paid by the page. A card is rented by the hour, whether it reads one page or its fill. Below some volume the API is cheaper; above it, the card. Choose the model, put in what you pay, and how hard you would run the card; the measured throughput does the rest.

      What a bad scan does

      The same pages, degraded in four reproducible steps of noise, blur, skew and lost contrast, calibrated to what they do to OCR's word accuracy. Level 0 is the clean page. The vision models read the pixels and barely notice; the pipelines that read OCR's text lose almost everything.

      Two of the extra training runs, same data and recipe but a different random seed, learned to wrap their answers in the prompt's schema instead of answering.       What did not work

      Four designs the measurements turned down, each tried before it was dropped.

      Forcing the output into the schema's grammar

      Meant to guarantee valid JSON. It pushed the models off the format they were trained on, so outputs are read freely.

      Half the visual tokens a page

      Saved a few cents a thousand pages and cost points of fields right on every form type measured, as the recipe chart shows.

      The fine-tune's own token probability as a confidence signal

      Set to keep accepted fields 99% right, it still sent almost every test field to a person. It is confidently wrong.

      Quantising the vision tower

      The first run that stored the image encoder in 4 bits failed at its first step. The tower now stays at full precision.

      The evidence is in docs/rejected.md.

      What this does not show

      Nothing reached 99% unattended. To let a field through without a person, a reader has to know when it is right. Two signals were tried: whether a frontier model's read of the image agrees with its read of the OCR text, and the fine-tune's own token probability. Set on the development pages to keep accepted fields 99% right, both sent of test fields to a person.

      • Old, public, printed forms. FARA registrations from the 1960s on, FCC ad-buy orders, Indonesian receipts and NIST's synthesised 1988 tax forms. No handwriting, no long documents, no form whose type is unknown.
      • Small test sets on two form types. CORD's 100 test receipts and NIST's 500 pages over twenty form faces are too few for the release gate to decide field by field at three points, so its verdict there is "not decided", not "pass".
      • The release gate blocks the fine-tunes on registration and ad-buy forms against the frontier models: . They are cheaper, not equivalent.
      • Prices move. Every price here carries the day it was read, and the calculator takes your own.
      • Training is not in the cost per page. Neither the fine-tune's rented hours nor Azure's training hours ( past its free hours) are in the per-page figures; both are one-off costs to spread over the months you run.

      How this was built

      I designed this project and made the calls in it: which readers to put side by side, which pages carry which claim, and what to do when a result came back wrong. I came to it after eight years of building machine learning inside government. I tested the fine-tunes on form designs they never saw in training, because a fine-tune learns the layouts it is shown. That held up: they lose points on unseen designs and the frontier models do not. Partway through I added Azure Document Intelligence as a sixth reader, because it is the product a buyer is quoted first, and the headline now rests on that comparison. When the fine-tunes' first reads came back without token probabilities, I had the test sets read a second time with them rather than drop the measure of how many fields a person must still check. That second read is how I know the answer is almost all of them.

      I used an AI coding assistant (Claude Code) for implementation and drafting, which is now standard practice in software, data science and machine learning work. Every number on this page can be reproduced from the repository with one command, and the plan was written before the first line of code. The diagrams, and what each part of the system does, are on the architecture page.

      Several pieces come from my earlier projects: the fine-tuning recipe, the Gemma bases and the break-even arithmetic from Frontier Quality at a Fraction of the Bill, the gateway and its cost ledger from Inside the Boundary, On the Record, and the release gate from AI Release Gate.

      Glossary
      2B, 4B
      The size of a model, in billions of learned numbers (parameters). Gemma 4 E2B and E4B are small enough to run on one consumer graphics card.
      Adapter (LoRA)
      A small set of extra weights trained beside a frozen model. Only the adapter changes, so training is cheap and the base model stays as it was.
      Bootstrap interval
      A range for a result, found by re-scoring many random resamples of the test documents. A 95% interval is built to hold the true value 95 times in 100.
      Frontier model
      The largest general-purpose AI models from the big vendors, here Claude, GPT and Gemini, used through their paid APIs.
      Invented value
      A value written for a field the page leaves blank. On a form a person signs off, a blank costs less than a confident wrong value.
      OCR
      Optical character recognition: software that turns a scanned image into text. Here, Tesseract.
      Open weights
      A model whose weights are published, so anyone can run and fine-tune it on their own hardware.
      QLoRA
      Training an adapter on a base model whose weights are stored in 4 bits, so a vision model fits on one 24 GB card.
      Release gate
      A statistical test that decides whether a cheaper model is no worse than a reference within a set margin, or declines to decide when there are too few documents.
      Requests in flight
      How many documents are being read at the same moment. More in flight means more pages a second, and a longer wait for each one.
      Visual tokens
      The pieces a vision model cuts a page image into. More tokens show finer detail and cost more to process.
